# 决策记录：文档生命周期与双语机制

- 日期：2026-09-15
- 状态：已接受
- 背景：文档库需要解决三件事——历史版本保留（归档）、新鲜/过时标识、防篡改；同时文档需支持中英双语。关联：根目录 AGENTS.md（Document Lifecycle / Bilingual Rules 两节）、`scripts/check-docs.sh`。

## D6 归档采用 git 标签，不建归档文件夹

- **决定**：历史保留完全依赖 git（天然永久保存每个版本）；每月打存档标签 `archive-YYYY-MM` 并推送远端作为阶段快照。
- **理由**：搬"归档文件夹"会造成同一文档两份副本，违反"一个知识一个家"铁律，且旧副本不会随新文档更新。标签是零成本快照，翻旧版一条命令。
- **否决的备选**：archive/ 目录 + 复制旧文件（双份真相，必腐烂）。

## D7 新鲜/过时标识用"状态行 + git 时间"，否决人写版本号

- **决定**：每份文档头部一行 `> status:`（生效 / 已过时 → 看xxx / 已废弃）；最后修改时间由 git 自动记录。
- **理由**：新鲜度本质是"还算不算数"（有效性），不是时间——昨天的文档可能错，去年的可能有效，时间只做参考。人手维护版本号必忘记更新，错误版本号比没有更危险。
- **否决的备选**：文档头部手写 v1.0/v1.2 版本号。

## D8 防篡改采用三层：哈希链 + 远端禁改写 + 自动体检

- **决定**：第一层 git 哈希链（自动，改动必留痕）；第二层远端（GitHub）分支设置**禁止 force push、禁止历史改写**（一次性人工配置）；第三层 `scripts/check-docs.sh` 在提交/PR 时自动运行（链接有效性、双语配对、翻译新鲜度、超期文档提醒）。
- **理由**：哈希链保证"改了必被发现"；远端禁改写保证"本地篡改推不上去"；体检脚本把"知识库新鲜度"从口号变成机械门禁（对应 OpenAI 实践：用 CI 校验知识库结构与新鲜度）。
- **可选加强（未启用，见 B8）**：GPG 签名提交（证明作者身份）、SHA256 清单（向仓库外交付时的完整性证明）。

## D9 双语采用 zh 权威 + en 翻译，`.zh.md`/`.en.md` 后缀区分

- **决定**：命名 `*.zh.md` / `*.en.md` 成对同目录；**中文为权威版本**，英文为翻译；改中文必须同步英文，来不及先在英文版标注"落后"。首批英文版覆盖：根 README、docs 文档地图、调研篇、实施篇；内部活文档（决策/模板/适配卡/计划）默认仅中文。
- **理由**：双语双写成本翻倍，必须指定权威方避免两个版本各自漂移；按需翻译把翻译成本限制在真正有英文读者的文档上。
- **否决的备选**：`en/`、`zh/` 镜像目录（文件数翻倍、配对关系不直观）；不指定权威（必然漂移）。
- **触发扩展**：全量双语化见 B9。
